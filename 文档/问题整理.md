## 001｜员工条件分页查询

- 问题：`selectAllByOther` 返回 `List<Emp>`，但当时 SQL 写的是 `SELECT count(0)`，只返回数量，不能映射员工明细。
- 另一个可能原因：搜索条件输入不匹配，`AND` 要求全部条件成立。用户后来怀疑当时条件输入有误，具体请求的直接原因未确认。
- 筛选参数可不传时，使用 MyBatis `<if>` 按需添加条件；`NULL` 参与普通比较不会表示“忽略条件”。
- `FROM dept d, emp e WHERE d.id = e.dept_id` 与显式 `INNER JOIN ... ON ...` 在本例的内连接中等价；改写连接形式主要是为了可读性。
- 列表查询应返回 `e.*` 和 `d.name AS dept_name`；项目的驼峰映射可将 `dept_name` 映射为 `deptName`。PageHelper 自动生成计数 SQL 属于正常分页流程。
- XML 中 `&gt;=` 表示 `>=`，`&lt;=` 表示 `<=`；普通 XML 文本中的 `<` 需要转义。
- 验证：使用构造的匹配参数，在原 Mapper 中复现 `total=1、rows=[null]`；修正后的查询通过 H2 场景检查及本机 MySQL 只读核对。原始具体搜索条件没有复现确认。

## 002｜Java 26 反射修改 final 字段警告

- 现象：`BoundSql.parameterMappings` 被 `SetFieldInvoker` 反射修改，Java 26 发出警告。
- 原因：当时本机缓存的 PageHelper 5.3.3 在分页处理中替换参数映射列表；JDK 26 默认警告，当前允许执行，未来版本默认会限制。终端当时为 Java 26.0.1，运行 JDK 与项目编译目标应分别检查。
- `final` 修饰引用时限制重新赋值，不保证对象内部内容不可变。
- 兼容选项 `--enable-final-field-mutation=ALL-UNNAMED` 放在 JVM 参数中；它允许相关反射行为，并未消除底层依赖。需要具体调用栈时可用 `--illegal-final-field-mutation=debug`。
- 参考：[Oracle JDK 26 迁移说明](https://docs.oracle.com/en/java/javase/26/migrate/preparing-final-field-mutation-restrictions.html)。当时没有修改启动选项或升级依赖。

## 004｜日志路径写死导致另一台电脑启动报错

- 问题：`logback.xml` 原先写死 `E:/log/...`，另一台电脑没有 E 盘，出现 `FileNotFoundException`。
- 用户已将日志路径改为：

```xml
<fileNamePattern>${TLIAS_LOG_DIR:-./logs}/tlias-%d{yyyy-MM-dd}-%i.log</fileNamePattern>
```

- 未设置 `TLIAS_LOG_DIR` 时使用工作目录下的 `./logs`；需要自定义时，可在 IDEA 运行配置的环境变量中设置该变量。默认值随配置文件交付，不要求每台电脑设置相同盘符。
- 应修改 `src/main/resources/logback.xml` 后重新构建；`target/classes` 是构建产物。当时未验证两台电脑均可启动。

## 005｜IDEA 中 Lombok 生成的方法标红

- 原因：当时项目已有 Lombok 依赖且该模块注解处理已启用，但当前 IDEA 缺少 Lombok 插件，未识别 `@Data` 和 `@AllArgsConstructor` 生成的成员。
- 用户处理插件后反馈标红已消失；这不等于完整构建、数据库和接口均已验证。
- 内网开发需分别准备与 IDEA 版本匹配的 Lombok 插件、JDK 21、Maven 及项目所需的依赖和构建插件。可在联网环境准备后使用 `mvn -o clean package -DskipTests` 验证特定构建能否离线完成；内网可用 Maven 仓库时应配置镜像，不必启用离线模式。
- 参考：[Lombok IDEA 设置](https://projectlombok.org/setup/intellij)、[Maven 离线准备](https://maven.apache.org/plugins/maven-dependency-plugin/go-offline-mojo.html)。

## 007｜文件上传：参数类型、异常和保存路径

- 当时 `UploadController` 中 `transferTo` 传入字符串导致报红。该方法接收 `File` 或 `Path`，可使用 `new File(...)`；随后需要捕获或声明 `IOException`。
- 用户后来选择 `try-catch`，并将 `IOException` 包装为 `RuntimeException` 向上抛出。写入失败时，后面的“上传成功”不会执行。
- `new File(...)` 只创建路径对象；上传目录需要存在或由代码创建，目标文件由 `transferTo` 写入。
- 普通 Java 文件路径通常相对 `user.dir`；当前默认 Tomcat 的 `transferTo(File)` 会将相对路径交给 multipart 位置处理，默认可能是应用临时目录。想以工作目录为基准，可先将 `File` 转为绝对路径再传入。
- `src/main/resources` 适合随应用发布的资源；运行时上传文件通常放在独立可写目录。打包部署后 classpath 资源不一定是可写的普通文件目录。

以下是尚未在项目中实施或测试的单机设置示例：

```yaml
app:
  upload-dir: E:/web-management-data/uploads
```

```java
// 导入 Value、Path、Files 和 UUID
@Value("${app.upload-dir}")
private String uploadDir;

// 放入原有的 try 块
Path directory = Path.of(uploadDir).toAbsolutePath().normalize();
Files.createDirectories(directory);
String storedName = UUID.randomUUID().toString();
file.transferTo(directory.resolve(storedName));
```

`app.upload-dir` 是自定义配置，必须由代码读取；示例的存储名没有扩展名。文件保存后也不会自动获得 HTTP 访问地址。多实例场景可考虑共享存储或对象存储。参考：[Spring 上传文件示例](https://spring.io/guides/gs/uploading-files/)。
