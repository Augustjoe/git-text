## 001｜员工条件分页查询结果不正确

- 记录日期：2026-10-23
- 项目：`E:\gitTest\git-text\JavaTestDemo01\web-management`
- 接口：`GET /emp`
- 现象：使用下面的 SQL 查询员工时，结果不符合预期。
- 后续反馈：用户再次尝试后，怀疑原先输入的搜索条件有误。目前尚未确认复测时是否保持了同一份 SQL，因此当次请求筛选为空的直接原因仍待确认。下文确认的计数结果与员工对象映射问题，应与输入条件不匹配的问题分开理解。

```sql
SELECT count(0)
FROM dept d, emp e
WHERE d.id = e.dept_id
  AND e.name LIKE CONCAT('%', #{name}, '%')
  AND e.gender = #{gender}
  AND e.entry_date BETWEEN #{begin} AND #{end}
ORDER BY e.update_time DESC
```

### 一、定位到的代码

| 文件（相对项目根目录） | 作用 | 本次结论 |
| --- | --- | --- |
| `src/main/java/com/webDemo/controller/EmpController.java` | 接收分页和筛选参数 | 姓名、性别和日期允许不传，需要 SQL 配合处理 |
| `src/main/java/com/webDemo/service/impl/EmpServiceImpl.java` | 启动 PageHelper，组装 `total` 和 `rows` | 紧接着调用列表查询的流程正确 |

| `src/main/java/com/webDemo/pojo/Emp.java` | 接收员工字段 | 包含 `entryDate`、`deptId`、`deptName` 等属性 |

调用过程：

```text

  → EmpServiceImpl.page(...)
  → PageHelper.startPage(page, size)

  → PageResult<Emp>：total + rows
```

### 二、原因分析

#### 1. 列表查询误写成了统计查询（主要原因）

Java 方法返回的是：

```java
List<Emp> selectAllByOther(...);
```

XML 声明每一行映射成一个员工对象：

```xml
<select id="selectAllByOther" resultType="com.webDemo.pojo.Emp">
```

但 `SELECT count(0)` 只返回一个数量，没有查询员工的 `id`、`name`、`gender` 等字段。SQL 的结果结构与 Java 的返回类型不匹配。

假设符合条件的员工有 12 人：

- `SELECT COUNT(*) ...` 返回一行数量 `12`。
- `SELECT e.*, d.name AS dept_name ...` 才返回这 12 人的明细。

本机 MySQL 只读对照验证中，原 Mapper 配合现有 Service 分页流程、在不传筛选条件时返回了 `total=1`、`rows=[null]`：PageHelper 对聚合查询的结果行计数，而这一行数量又无法映射为有效的员工对象。这是本次实际复现的错误结果。

`count(0)` 本身是合法的计数表达式：常量 `0` 不是 SQL 的 `NULL`，因此每行都会被计入。本例中换成 `count(*)` 仍然不能解决“要员工列表，却只查询数量”的问题。没有匹配员工时，无 `GROUP BY` 的计数查询仍返回一行，值为 `0`。见 [MySQL COUNT 说明](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)。

#### 2. 可选条件被无条件拼接（另一处直接问题）

Controller 中 `name`、`gender`、`begin`、`end` 可以不传。原 SQL 却始终使用这些参数。

例如不传性别时，相当于执行：

```sql
AND e.gender = NULL
```

SQL 中这不表示“不筛选性别”，而是得到未知的比较结果，不能通过 `WHERE` 筛选。同理，姓名为 `NULL` 时原来的 `LIKE` 条件无法正常匹配；原来的日期范围也不支持独立的开始或结束日期。

正确做法是：参数有值才追加对应条件。注意，“参数为空时忽略筛选”与“查询数据库中值为空的记录”是两种需求；后者应明确使用 `IS NULL`。见 [MySQL NULL 说明](https://dev.mysql.com/doc/refman/8.4/en/working-with-null.html)。

#### 3. 统计查询不需要按员工字段排序

原 SQL 没有 `GROUP BY`，只返回一个总数，按员工更新时间排序没有业务意义。如果只是统计数量，应去掉 `ORDER BY`。本接口需要员工列表，所以保留排序并改为查询明细。

MySQL 8.4 文档还规定了 `ONLY_FULL_GROUP_BY` 下聚合查询引用非聚合排序字段的限制，其他环境可能因此报错；但本机实测中，该模式已开启，原 SQL 仍被接受，不能将排序断言为本次实际报错原因。见 [MySQL 聚合与分组规则](https://dev.mysql.com/doc/refman/8.4/en/group-by-handling.html)。

#### 4. 内连接会过滤没有匹配部门的员工（需要理解的业务规则）

原来的 `FROM dept d, emp e WHERE d.id = e.dept_id` 是隐式内连接。员工未分配部门，或 `dept_id` 指向不存在的部门时，不会出现在结果中。

本次将其改为等价的显式 `INNER JOIN`，保留已有业务行为。如果以后要求“所有员工都要显示，没有部门时部门名称为空”，应改成 `LEFT JOIN dept d ON d.id = e.dept_id`，并让列表和统计使用一致规则。这是业务选择，不能仅凭结果数量较少就断定连接方式错误。

### 补充追问：四个参数都传了，为什么仍然没有员工数据？

如果 `name`、`gender`、`begin`、`end` 都已正确绑定且非空，前面“空参数参与筛选”的原因就不适用。但 `COUNT(0)` 与 `List<Emp>` 不匹配的问题依然存在。

再次使用本机数据库中已有员工的姓名、性别和入职日期构造四个非空参数（开始日、结束日均为该员工入职日），只读复现结果如下：

```text
四个参数：均非空
原 SQL 的 COUNT(0)：1，说明确实匹配到了员工
原 Mapper + PageHelper：total=1，rows=[null]
```

原因是 `WHERE` 决定哪些记录符合条件，`SELECT` 决定最终返回哪些内容。原 SQL 即使筛选成功，也只返回数量 `1`，没有返回员工字段；MyBatis 无法把这个计数列映射成有效的 `Emp` 对象。修复的关键仍是把列表查询的 `SELECT count(0)` 改为 `SELECT e.*, d.name AS dept_name`。

需要区分两种结果：

- `COUNT(0)` 大于 0，但接口没有员工明细：检查查询列与返回类型，本次已经复现这一问题。
- `COUNT(0)` 等于 0：说明完整条件没有匹配到记录，需要结合当次实际参数核对姓名、性别取值、入职日期区间以及部门是否匹配；`AND` 要求所有条件同时成立。

上述验证使用构造的匹配参数，不等同于确认用户当时那一组具体参数也一定匹配；定位某次请求需要该请求的实际参数值。

### 补充追问：为什么改成 INNER JOIN？原来的连接方式能用吗？

**原来的两表连接方式可以使用。改成 `INNER JOIN` 是为了清楚表达表之间的关联，不是修复本次问题必须进行的改动。**

本次有两种不同目的的修改：

| 修改 | 目的 |
| --- | --- |
| `SELECT count(0)` 改成 `SELECT e.*, d.name AS dept_name` | 查询员工明细和部门名称，使结果结构与 `List<Emp>` 一致 |
| `FROM dept d, emp e WHERE d.id = e.dept_id` 改成显式 `INNER JOIN` | 把表关联条件单独放到 `ON` 中，提高可读性；当前两表内连接匹配的记录不变 |

保持查询字段一致时，以下两种连接写法在本例中等价：

```sql
-- 隐式内连接：原来的连接方式，合法
SELECT e.*, d.name AS dept_name
FROM dept d, emp e
WHERE d.id = e.dept_id;

-- 显式内连接：用 ON 表达关联条件
SELECT e.*, d.name AS dept_name
FROM emp e
INNER JOIN dept d ON d.id = e.dept_id;
```

逐项理解：

- `emp e`：给员工表起别名 `e`；`dept d`：给部门表起别名 `d`。
- `e.*`：选择员工表的全部字段，不包含部门表的全部字段。
- `d.name AS dept_name`：额外选择部门名称，并把这列的结果名称设为 `dept_name`；不会修改数据库原字段名称。
- 项目已开启驼峰映射，因此结果列 `dept_name` 能映射到 `Emp.deptName`，员工姓名 `e.name` 则映射到 `Emp.name`。
- `ON d.id = e.dept_id`：员工的部门 ID 与部门表 ID 相等时，将两条记录关联起来。
- 使用显式内连接时，`ON` 表达表关联，后续 `WHERE` 可以集中表达姓名、性别和日期等业务筛选条件。

两种写法都会排除没有匹配部门的员工，换成 `INNER JOIN` 不会自动解决“无部门员工未显示”的问题。这里的等价说明针对当前两表内连接，不应直接套用到外连接中移动条件的情形。

学习时可以先保留原来的连接写法，只调整 `SELECT` 查询字段，再验证是否能够返回员工明细。不要将改善可读性的修改误认为原写法存在语法错误。

### 补充反馈：搜索条件可能输入有误

用户反馈：“我又尝试了下好像我之前的搜索条件输入错了”。这是新的排查线索，目前应标注为待确认。

- **输入条件问题**：如果在同一份 SQL 下，仅纠正搜索条件就能匹配到记录，说明先前的条件没有同时满足数据库中的数据要求。几个条件用 `AND` 连接时，必须全部满足。
- **代码映射问题**：源码中的 `SELECT count(0)` 与 `List<Emp>` 不匹配仍是已确认的问题；它影响能否返回员工对象，不能据此断定用户当时的搜索条件已经匹配到了记录。
- **确认方式**：核对本次是否只改了搜索条件，还是同时使用了修改后的 SQL；记录同一份 SQL 下，修改输入前后的实际结果。

教学结论：应先明确“没有匹配到记录”还是“匹配到了但接口没有员工明细”，再对应检查条件输入和结果映射。此前仅凭映射问题推断某次筛选失败的直接原因，证据不足。

### 三、实际修复

#### 1. 修改 EmpMapper.xml

```xml
<select id="selectAllByOther" resultType="com.webDemo.pojo.Emp">
    SELECT e.*, d.name AS dept_name
    FROM emp e
    INNER JOIN dept d ON d.id = e.dept_id
    <where>
        <if test="name != null and name != ''">
            AND e.name LIKE CONCAT('%', #{name}, '%')
        </if>
        <if test="gender != null">
            AND e.gender = #{gender}
        </if>
        <if test="begin != null">
            AND e.entry_date &gt;= #{begin}
        </if>
        <if test="end != null">
            AND e.entry_date &lt;= #{end}
        </if>
    </where>
    ORDER BY e.update_time DESC
</select>
```

- 查询员工字段，同时为部门名称设置别名 `dept_name`，避免与员工姓名 `name` 混淆。
- 姓名为 `null` 或空字符串时忽略姓名筛选；仅含空格的姓名目前仍作为实际搜索内容。
- 性别只判断 `null`；不要给 `Integer` 参数套用字符串的空串判断。
- 日期条件分别判断，支持单侧边界；两侧都有时包含开始日和结束日。
- `<where>` 在有条件时添加 `WHERE`，并移除开头多余的 `AND`；全部条件为空时不会生成空的 `WHERE`。见 [MyBatis 动态 SQL](https://mybatis.org/mybatis-3/dynamic-sql.html)。

#### 2. 为 Mapper 多参数补充 @Param

```java
import org.apache.ibatis.annotations.Param;

List<Emp> selectAllByOther(@Param("name") String name,
                          @Param("gender") Integer gender,
                          @Param("begin") LocalDate begin,
                          @Param("end") LocalDate end);
```

这样 XML 中的参数名明确绑定到 Java 方法参数，不依赖编译时是否保留参数名称。这是稳定性补充；本次没有发现实际的“参数找不到”报错，不能把缺少 `@Param` 断言为已发生的根因。见 [MyBatis 多参数说明](https://mybatis.org/mybatis-3/java-api.html)。

#### 3. 保留已有分页流程

```java
PageHelper.startPage(page, size);
List<Emp> emps = empMapper.selectAllByOther(name, gender, begin, end);
Page<Emp> p = (Page<Emp>) emps;
return new PageResult<Emp>(p.getTotal(), p.getResult());
```

在当前使用方式下，PageHelper 会处理总数统计和分页，Mapper 应提供明细查询。`startPage` 后紧接着的第一个 MyBatis 查询会被分页，不要在两者之间插入其他查询。见 [PageHelper 使用说明](https://github.com/pagehelper-org/Mybatis-PageHelper/blob/master/wikis/en/HowToUse.md)。

排查日志时要区分两种 SQL：PageHelper 自动生成的 `SELECT count(0) ...` 可能完全正常；这次的问题是源码里的明细查询本身被写成了 `count(0)`。

### 四、涉及的 Java / MyBatis 知识点

| 知识点 | 本次如何体现 |
| --- | --- |
| 分层调用 | Controller 接收参数，Service 组织分页，Mapper 查询数据库 |
| 泛型 `List<Emp>` | 表示多条员工记录；单个统计数量应由独立的 `Long` 等类型接收 |
| `resultType` | 指集合中每一行的对象类型，此处是 `Emp`，不是 `List` |
| `@Param` | 为 Mapper 的多个参数指定 XML 可使用的名字 |
| 引用类型与 `null` | `Integer`、`LocalDate` 可以表示未提供的筛选条件 |
| `#{参数}` | MyBatis 绑定预编译参数，不应改为 `${参数}` 拼接用户输入 |
| 动态 SQL 与 OGNL | `<if test="...">` 按条件生成 SQL；这里的表达式由 MyBatis 解析 |
| 驼峰映射 | 项目已开启 `map-underscore-to-camel-case`，`dept_name` 对应 `deptName` |
| 日期类型 | `LocalDate` 适合入职日期；`LocalDateTime` 适合创建和更新时间 |
| 请求日期转换 | `@DateTimeFormat(pattern = "yyyy-MM-dd")` 将请求字符串转为 `LocalDate` |
| XML 转义 | XML SQL 中使用 `&lt;=` 表示 `<=`，`&gt;=` 表示 `>=` |
| 分页结果 | `total` 是全部符合条件的记录数，`rows.size()` 是当前页实际返回数量 |

#### 补充：XML 中的 &gt; 和 &lt; 是什么？

Mapper XML 中的 `&gt;`、`&lt;` 是 XML 实体引用，也常称为转义字符。完整写法都包含末尾的分号 `;`。

| XML 中的写法 | 表示的符号 | 含义 |
| --- | --- | --- |
| `&gt;` | `>` | 大于 |
| `&lt;` | `<` | 小于 |
| `&gt;=` | `>=` | 大于等于 |
| `&lt;=` | `<=` | 小于等于 |

例如项目中的日期条件：

```xml
AND e.entry_date &gt;= #{begin}
AND e.entry_date &lt;= #{end}
```

XML 解析后，SQL 的条件含义是：入职日期大于等于开始日期，并且小于等于结束日期，两端日期都包含在内。

这样写是因为 SQL 位于 XML 文件中，`<` 在 XML 普通文本中会被当作标签的开始，表示小于号时需写为 `&lt;`。`>` 在这里通常可以直接书写，写成 `&gt;` 也合法，能保持风格一致。这是 XML 的书写规则，SQL 的比较运算含义没有改变。

补充：如果以后要手动统计，应定义独立的计数方法，返回 `Long`，并让计数 SQL 与列表 SQL 使用相同的筛选和连接规则。当前分页流程不需要额外调用已有的无条件 `count()` 方法。

### 一、这些警告是什么意思？

| 警告内容 | 含义 |
| --- | --- |
| `Final field parameterMappings ... has been mutated reflectively ... SetFieldInvoker` | MyBatis 的反射工具修改了 `BoundSql` 中用 `final` 声明的参数映射字段 |
| `Use --enable-final-field-mutation=ALL-UNNAMED ...` | JVM 提供了启动选项，可显式允许普通 classpath 上代码的这类操作 |
| `Mutating final fields will be blocked in a future release ...` | 未来的 Java 版本会默认限制未获授权的此类操作，需提前关注兼容性 |

JDK 26 开始对此类反射操作发出警告，当前默认模式仍允许执行。因此，这三行警告本身不表示程序已经停止，也不能用来判断搜索条件或 SQL 语法有误。依据：[Oracle JDK 26 迁移说明](https://docs.oracle.com/en/java/javase/26/migrate/preparing-final-field-mutation-restrictions.html)。

### 二、结合当前项目理解触发过程

已核对的信息：

- 本机终端 `java -version` 输出为 `26.0.1`。
- 项目 `pom.xml` 中的 `<java.version>` 为 `25`。构建目标版本不等于实际启动程序使用的 JDK；IDE 的启动 JDK 需要单独核对。
- 警告中明确指出 MyBatis 版本为 `3.5.19`。
- 本机 PageHelper 5.3.3 的 `MySqlDialect.processPageParameter` 会创建包含分页参数的新参数映射列表，再调用 `metaObject.setValue("parameterMappings", newParameterMappings)`。
- MyBatis 的 `SetFieldInvoker` 最终使用反射的 `Field.set` 写入字段。

MyBatis 的 `BoundSql` 保存待执行的 SQL 和参数信息，其中字段声明为：

```java
private final List<ParameterMapping> parameterMappings;
```

见 [MyBatis 3.5.19 的 BoundSql 源码](https://github.com/mybatis/mybatis-3/blob/mybatis-3.5.19/src/main/java/org/apache/ibatis/mapping/BoundSql.java)。

`parameterMappings` 描述 SQL 中 `?` 占位符如何绑定参数。分页插件增加 `LIMIT ?` 或 `LIMIT ?, ?` 时，也需要补充分页参数的映射信息。本机依赖源码中可见一条直接对应警告的触发路径：

```text
PageHelper 处理分页参数
  → 创建新的参数映射列表
  → 通过 MyBatis 的 MetaObject 写入 parameterMappings
  → SetFieldInvoker 使用反射替换 final 字段的引用
  → Java 26 发出警告
```

仅凭警告不能列出完整的上层调用栈；若要确认某次具体运行的调用来源，可以使用下文的诊断选项。

### 三、Java 知识点：final 引用与对象内容

`final` 修饰引用变量时，限制的是该变量不能在初始化后重新指向另一个对象，不代表对象内部内容一定不能改变。

```java
final List<String> names = new ArrayList<>();
names.add("张三");                // 可以：修改列表内容
// names = new ArrayList<>();     // 编译错误：重新给 final 变量赋值
```

本例触发警告的操作，是框架通过反射替换 `parameterMappings` 字段所引用的列表。不要为了消除警告去修改自己的 `Emp` 字段，警告涉及的是依赖库内部的字段。

### 四、如何处理：先理解，再自行选择

如果接口仍然正常，可以先继续学习，并记录这个兼容性问题。长期应检查依赖是否存在避免修改 `final` 字段的兼容实现，不能保证任意升级一个版本就一定解决。

如果暂时保留当前依赖，需要显式允许该行为，可以手动向 Java 启动命令或 IDE 的 **VM options（虚拟机选项）** 添加：

```text
--enable-final-field-mutation=ALL-UNNAMED
```

这是授予运行权限的兼容选项，不是修复 SQL 或消除底层反射写入行为。`ALL-UNNAMED` 指普通 classpath 上的代码所在的未命名模块。该选项放在 JVM 参数中，不是 `main` 方法的程序参数，也不写进 Mapper XML。依据：[Java 26 启动参数说明](https://docs.oracle.com/en/java/javase/26/docs/specs/man/java.html)。

如果需要定位完整调用链，可以在诊断时使用：

```text
--illegal-final-field-mutation=debug
```

此诊断选项会输出调用栈，不是消除警告的选项。

如果学习环境原计划使用 Java 25，可自行核对 IDE 的启动 JDK 是否与计划一致。仅修改 `pom.xml` 中的版本数字不会切换实际运行环境；换用旧运行时避开新警告，也不代表框架内部的写入方式已经改变。

- 本次读取了版本配置、本机 JDK 版本及缓存的依赖源码，并核对 Oracle 官方说明。

- `WARNING`、抛出的异常以及查询结果不符合预期，应分别判断，不能仅凭警告文字就认定它是搜索失败的原因。

### 二、为什么 JSON 要这样写？
